    {{ icon('compass') }} Help

    Guided tour

    Follow one certificate through its whole life: request, approval, download, signing a file, verifying it, and revocation. It takes about ten minutes. Each stop says what to do, and what the PKI is doing behind the scenes.

    {{ icon('check-circle') }} Before you start

    • {{ icon('check-circle' if ca_ready else 'alert') }} The CA exists. {% if ca_ready %}Done: the Root CA and the Issuing CA have been created. {% else %}Not yet: run python scripts/bootstrap_ca.py with ROOT_CA_PASS and ISSUING_CA_PASS set, then restart the portal.{% endif %}
    • {{ icon('check-circle' if ca_ready and ca_key_available else 'alert') }} The Issuing CA key can be unlocked. {% if ca_ready and ca_key_available %}Done: approvals and revocations will work. {% else %}Set ISSUING_CA_PASS in the terminal that runs python run.py.{% endif %}
    • {{ icon('file') }} Something to send (optional). python scripts/make_sample_csrs.py writes ready-made certificate requests into demo_work/. Or skip it and use demo mode in step 2.

    {{ icon('users') }} Who does what

    • ApplicantA student or faculty member who wants a certificate.
    • RA officerChecks the applicant's identity and approves or rejects. Signs nothing.
    • AnyoneCan check a signed file or a certificate's status. Needs no account.
      {% call step(1, 'applicant', 'Choose who you are', 'Request a certificate') %}

      Do this: open Request a certificate and pick I am a student or I am faculty.

      {{ icon('shield-check') }}Behind the scenes: your role decides which certificate types you may ask for. Students: login and code signing. Faculty: e-mail (S/MIME), code signing and TLS server.

      Open this page {{ icon('arrow-right') }} {% endcall %} {% call step(2, 'applicant', 'Fill in your details and choose your key', 'Request a certificate') %}

      Do this: type your name, VIT e-mail and registration number, and pick a certificate type. Then either upload a CSR (for example one from demo_work/) or tick demo mode. To try signing later in this tour, choose Code and document signing with demo mode.

      {{ icon('shield-check') }}Behind the scenes: the portal checks the CSR straight away. Its signature proves you hold the private key, and the key must be big enough for the type. The name inside the CSR is ignored: the certificate will carry the details the RA verifies.

      Open this page {{ icon('arrow-right') }} {% endcall %} {% call step(3, 'applicant', 'Keep your tracking ID', 'Track a request') %}

      Do this: after submitting you land on your status page, with an ID like REQ-3F9A1C07B2D4. Bookmark the page or write the ID down; Track a request brings you back.

      {{ icon('shield-check') }}Behind the scenes: the ID is random (48 bits), so nobody can guess someone else's request. The submission is written to the audit log.

      Open this page {{ icon('arrow-right') }} {% endcall %} {% call step(4, 'ra', 'Review and approve the request', 'RA dashboard') %}

      Do this: on the RA dashboard, compare the name, e-mail and registration number with the applicant's VIT ID card. Then press Approve and issue, or type a reason and press Reject.

      {{ icon('shield-check') }}Behind the scenes: on approval the Issuing CA signs the certificate. The subject comes from the verified details, every extension from the certificate type, and the serial number is 128 random bits. The Root CA is not involved: it stays offline.

      Open this page {{ icon('arrow-right') }} {% endcall %} {% call step(5, 'applicant', 'Download your certificate', 'Your status page') %}

      Do this: open your status page again and download cert.pem and chain.pem. In demo mode a password is shown once: write it down, then download cert.p12 (your key and certificate in one protected file).

      {{ icon('shield-check') }}Behind the scenes: the password is deleted from the server as soon as it has been shown, and the RA never sees it. chain.pem holds the Issuing CA and Root CA certificates, so anyone can check your certificate.

      Find your request {{ icon('arrow-right') }} {% endcall %} {% call step(6, 'applicant', 'Sign a file', 'Sign a file') %}

      Do this: on Sign a file, choose your code-signing .p12, type its password and pick any file, such as a PDF. You get back <file>.sig.json: keep it next to the file.

      {{ icon('shield-check') }}Behind the scenes: the portal signs the file's SHA-256 hash with RSA-PSS. Only code-signing certificates may sign. In real life you sign on your own computer with tools/sign_file.py, so your private key never leaves it.

      Open this page {{ icon('arrow-right') }} {% endcall %} {% call step(7, 'anyone', 'Verify the signature, then tamper with the file', 'Verify a signature') %}

      Do this: upload the file and its .sig.json on Verify a signature: all five checks pass and the signer is named. Now change a single character in the file and verify again.

      {{ icon('shield-check') }}Behind the scenes: the only thing trusted is the VIT Root CA certificate. The five checks are: the file hash, the signature, the chain to the Root CA, a code-signing certificate valid at signing time, and not revoked. One changed byte fails the first check.

      Open this page {{ icon('arrow-right') }} {% endcall %} {% call step(8, 'ra', 'Revoke the certificate', 'Certificates') %}

      Do this: under Certificates, open the code-signing certificate, choose a reason (for example keyCompromise) and press Revoke. Then verify the original, untouched file again.

      {{ icon('shield-check') }}Behind the scenes: the Issuing CA signs a new revocation list (CRL) with the next CRL number, published at /crl.pem, and the OCSP responder now answers "revoked". The signature fails check 5, even though the file never changed.

      Open this page {{ icon('arrow-right') }} {% endcall %} {% call step(9, 'ra', 'Read the audit log', 'Audit log') %}

      Do this: open the Audit log. Every step you just took is there, with who did it and when. Export CSV downloads the whole log.

      {{ icon('shield-check') }}Behind the scenes: accountability. An auditor can see who requested, approved, downloaded, signed and revoked, and in what order.

      Open this page {{ icon('arrow-right') }} {% endcall %}
